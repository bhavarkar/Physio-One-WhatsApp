# SECURITY & COMPLIANCE: WhatsApp AI Agent (Single Organization Edition)

## 1. Threat Model & Security Posture
The platform handles patient communications, appointment schedules, and contact details for Physio One. The security architecture adheres to defense-in-depth principles across transport, application, database, and third-party API integration layers.

---

## 2. Core Security Controls

### A. Authentication & Session Management
- **Password Hashing**: Argon2id with high memory cost (`time_cost=3`, `memory_cost=65536`, `parallelism=4`).
- **Token Storage**: JWT access tokens are delivered strictly via `HttpOnly`, `Secure`, and `SameSite=Strict` browser cookies. Tokens are never accessible to client-side JavaScript.
- **CSRF Defense**: Double-submit CSRF cookie token validated on all state-mutating requests (`POST`, `PUT`, `DELETE`).
- **Role-Based Access Control (RBAC)**: Enforced via FastAPI dependency injection at the endpoint level.

### B. WhatsApp Ingress & Webhook Security (Task 5)
- **Meta HMAC-SHA256 Verification**: Every incoming webhook payload from Meta Cloud API is cryptographically verified against the configured App Secret using the `X-Hub-Signature-256` header. Requests with invalid or missing signatures are rejected with HTTP 403 Forbidden.
- **YCloud HMAC-SHA256 Verification**: Webhook events from YCloud are verified using the `YCloud-Signature` header against the account's webhook secret.
- **Subscription Handshake**: Meta GET `hub.challenge` requests are verified against the stored `webhook_verify_token` per registered phone number.
- **Idempotency & Replay Defense**: Inbound event IDs (`entry[].id` or `id`) are checked against the `webhook_events` table before processing. Duplicate events are acknowledged with HTTP 200 without reprocessing.

### C. LLM Guardrails & Prompt Injection Defense
- **Zero Direct System Modification**: User prompts are treated strictly as untrusted input enclosed within distinct conversational message blocks.
- **Deterministic Action Gateways**: The LLM cannot directly modify the database. All actions require structured tool calls that pass through strict Pydantic validation and deterministic Python business logic.
- **Anti-Hallucination Disclaimers**: Deepti explicitly refuses to prescribe medicines, perform medical diagnoses, or override clinic policies (such as Sunday closures).

### D. Data Protection & Sensitive Credential Encryption (Task 5)
- **Fernet Symmetric Encryption at Rest**: Sensitive third-party API credentials (`whatsapp_accounts.access_token_encrypted`, `whatsapp_accounts.secret_key_encrypted`, and `ai_providers.api_key_encrypted`) are encrypted using Fernet (AES-128-CBC with HMAC-SHA256 data authentication) derived deterministically from the application master secret.
- **Secret Masking In APIs**: REST API endpoints for connection details and listings never expose raw access tokens or app secrets. Schemas return only boolean indicators (`has_access_token`, `has_secret_key`) and masked identifiers.
- **Audit Logging**: All administrative changes, role updates, manual appointment cancellations, and patient exports are recorded in the immutable `audit_logs` table.
- **PII Masking**: Logs generated by Celery and FastAPI sanitize patient phone numbers and full names (e.g. `+91 98*** **210`).

### E. Clinical Appointments & Availability Security (Task 6)
- **Least-Privilege RBAC**:
  - `Viewer` role has strictly read-only access (`appointments:read`). All mutation operations return HTTP 403 Forbidden.
  - Creation, rescheduling, updating, cancellation, completion, and marking no-shows require `Operator`, `Admin`, or `Super Admin` privileges.
- **CSRF Defense on Appointment Mutations**:
  - All state-mutating requests (`POST /api/v1/appointments`, `PATCH`, `/reschedule`, `/cancel`, `/complete`, `/no-show`) require a valid session cookie and a matching cryptographic `X-CSRF-Token` header.
- **Immutable Appointment History**:
  - Every lifecycle transition appends an immutable entry to `appointment_history` documenting previous/new states, timestamps, actor identity, and staff notes.
  - High-level security and administrative changes are simultaneously recorded in `audit_logs`.
- **Non-Destructive Operations**:
  - Appointment records and cancellation reasons are never physically deleted (`DELETE` method is omitted).
- **Public Slot Privacy**:
  - The availability endpoint (`/api/v1/appointments/availability`) returns only slot timestamps and availability status; patient identifiers, contact details, and clinical notes are never exposed.

## 3. Vulnerability Reporting & Patch Policy
- Regular dependency scanning via `pip-audit` and `npm audit`.
- Security patches are released with PATCH version bumps (e.g. `v1.0.1`) following the automated update pipeline.
