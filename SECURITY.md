# SECURITY & COMPLIANCE: WhatsApp AI Agent (Single Organization Edition)

## 1. Threat Model & Security Posture
The platform handles patient communications, appointment schedules, and contact details for Physio One. The security architecture adheres to defense-in-depth principles across transport, application, database, and third-party API integration layers.

---

## 2. Core Security Controls

### A. Authentication & Session Management
- **Password Hashing**: Argon2id with high memory cost (`time_cost=3`, `memory_cost=65536`, `parallelism=4`).
- **Token Storage**: JWT access tokens are delivered strictly via `HttpOnly`, `Secure`, and `SameSite=Strict` browser cookies. Tokens are never accessible to client-side JavaScript.
- **CSRF Defense**: Double-submit CSRF cookie token validated on all state-mutating requests (`POST`, `PUT`, `DELETE`).
- **Role-Based Access Control (RBAC)**: Enforced via FastAPI dependency injection at the endpoint level.

### B. WhatsApp Ingress & Webhook Security (Task 5)
- **Meta HMAC-SHA256 Verification**: Every incoming webhook payload from Meta Cloud API is cryptographically verified against the configured App Secret using the `X-Hub-Signature-256` header. Requests with invalid or missing signatures are rejected with HTTP 403 Forbidden.
- **YCloud HMAC-SHA256 Verification**: Webhook events from YCloud are verified using the `YCloud-Signature` header against the account's webhook secret.
- **Subscription Handshake**: Meta GET `hub.challenge` requests are verified against the stored `webhook_verify_token` per registered phone number.
- **Idempotency & Replay Defense**: Inbound event IDs (`entry[].id` or `id`) are checked against the `webhook_events` table before processing. Duplicate events are acknowledged with HTTP 200 without reprocessing.

### C. LLM Guardrails & Prompt Injection Defense
- **Zero Direct System Modification**: User prompts are treated strictly as untrusted input enclosed within distinct conversational message blocks.
- **Deterministic Action Gateways**: The LLM cannot directly modify the database. All actions require structured tool calls that pass through strict Pydantic validation and deterministic Python business logic.
- **Anti-Hallucination Disclaimers**: Deepti explicitly refuses to prescribe medicines, perform medical diagnoses, or override clinic policies (such as Sunday closures).

### D. Data Protection & Sensitive Credential Encryption (Task 5)
- **Fernet Symmetric Encryption at Rest**: Sensitive third-party API credentials (`whatsapp_accounts.access_token_encrypted`, `whatsapp_accounts.secret_key_encrypted`, and `ai_providers.api_key_encrypted`) are encrypted using Fernet (AES-128-CBC with HMAC-SHA256 data authentication) derived deterministically from the application master secret.
- **Secret Masking In APIs**: REST API endpoints for connection details and listings never expose raw access tokens or app secrets. Schemas return only boolean indicators (`has_access_token`, `has_secret_key`) and masked identifiers.
- **Audit Logging**: All administrative changes, role updates, manual appointment cancellations, and patient exports are recorded in the immutable `audit_logs` table.
- **PII Masking**: Logs generated by Celery and FastAPI sanitize patient phone numbers and full names (e.g. `+91 98*** **210`).

### E. Clinical Appointments & Availability Security (Task 6)
- **Least-Privilege RBAC**:
  - `Viewer` role has strictly read-only access (`appointments:read`). All mutation operations return HTTP 403 Forbidden.
  - Creation, rescheduling, updating, cancellation, completion, and marking no-shows require `Operator`, `Admin`, or `Super Admin` privileges.
- **CSRF Defense on Appointment Mutations**:
  - All state-mutating requests (`POST /api/v1/appointments`, `PATCH`, `/reschedule`, `/cancel`, `/complete`, `/no-show`) require a valid session cookie and a matching cryptographic `X-CSRF-Token` header.
- **Immutable Appointment History**:
  - Every lifecycle transition appends an immutable entry to `appointment_history` documenting previous/new states, timestamps, actor identity, and staff notes.
  - High-level security and administrative changes are simultaneously recorded in `audit_logs`.
- **Non-Destructive Operations**:
  - Appointment records and cancellation reasons are never physically deleted (`DELETE` method is omitted).
- **Public Slot Privacy**:
  - The availability endpoint (`/api/v1/appointments/availability`) returns only slot timestamps and availability status; patient identifiers, contact details, and clinical notes are never exposed.

### F. Multi-Provider LLM Gateway & Agent Runtime Security (Task 7)
- **Fernet Encryption & Masked Credentials**:
  - All LLM API keys (`ai_providers.api_key_encrypted`) are encrypted at rest using Fernet (AES-128-CBC + HMAC-SHA256).
  - API responses and frontend views mask API keys (e.g., `sk-proj...1234`), returning `has_api_key=true` without leaking raw secrets.
- **Controlled Tool Execution Sandbox**:
  - LLMs cannot execute arbitrary Python code, execute shell commands, run raw SQL, or invoke external HTTP endpoints.
  - All tool execution occurs through an explicit registry (`BaseTool`) with strict Pydantic parameter schemas, execution timeouts, and agent whitelist permissions.
  - Models requesting unregistered or unauthorized tools receive controlled denials recorded in execution logs.
- **PHI Masking in Tool Execution**:
  - Patient lookups and search tools sanitize and mask personal phone numbers in execution outputs to minimize data exposure.
- **Mutation Boundary & Sunday Invariant**:
  - No autonomous appointment creation, cancellation, or rescheduling is permitted in Task 7.
  - The read-only `check_availability` tool strictly routes through `AppointmentService`, enforcing Sunday closure and clinic operating hours (09:00 - 20:00 IST).
- **Safe Fallback Policy**:
  - Fallback provider invocation is disabled by default, triggers only on retryable network or rate-limit errors, and is explicitly forbidden if prior execution steps triggered mutating side-effects.
- **Context Budget Truncation & Loop Defense**:
  - Deterministic context truncation prevents prompt token overflow, always preserving the core system prompt and latest user inquiry.
  - Execution runtime enforces strict step limits (`max_execution_steps`) and timeouts (`execution_timeout_seconds`) to eliminate infinite tool execution loops.

### G. pgvector Memory, Knowledge Base & RAG Security (Task 8)
- **Patient Memory Isolation**:
  - Persistent conversation memories (`ConversationMemory`) are strictly isolated by `contact_id`.
  - Cross-patient memory leakage is architecturally prohibited; queries for patient memory require an explicit `contact_id` filter and cannot be accessed via general clinic FAQ retrieval.
  - Deletion of memory records is scoped strictly to the authorized contact.
- **Prompt Injection Defense**:
  - Retrieved knowledge chunks are treated as untrusted external data and wrapped in boundary tags (`<clinic_reference_document>` / `</clinic_reference_document>`) with explicit system instructions prohibiting documents from overriding core clinic rules or permissions.
- **Document Ingestion Security & Validation**:
  - Strict magic byte validation for PDF (`%PDF-`), DOCX (`PK\x03\x04` + `word/document.xml`), and plain text/markdown (binary null-byte check).
  - Maximum upload size enforced at 10 MB.
  - Zero external binary execution (uses pure Python ZIP/XML and stream parsing) preventing shell execution or native memory exploits.
- **Production Embedding Provider Guardrail**:
  - `DeterministicEmbeddingProvider` is explicitly tagged as a test-only provider (`is_test_provider=True`).
  - An explicit guardrail raises `EmbeddingError` if `ENVIRONMENT=production`, preventing mock/test embeddings from silently operating in production environments.
  - Vector dimensions (1536) are validated on every embedding generation to prevent index corruption.
- **Least-Privilege RBAC & CSRF Protection**:
  - Knowledge Base creation, document upload, reprocessing, archiving, and deletion require `Owner` or `Admin` privileges.
  - Semantic search and retrieval testing are restricted to `Operator`, `Admin`, and `Owner` roles.
  - All state-mutating document and knowledge base operations require valid CSRF double-submit token verification.

### H. Inbound WhatsApp AI Receptionist & Safety Orchestration (Task 9)
- **Default Inactive Safety Policy**:
  - `ai_mode` defaults strictly to `disabled` in `AIInboundSettings`. Both `shadow` and `live` modes require explicit, authenticated administrative activation (`Owner` or `Admin`).
  - At the completion of Task 9, live autonomous messaging is left in `disabled` state.
- **Opt-Out Compliance (TRAI & WhatsApp Policy)**:
  - Inbound messages containing opt-out keywords (`STOP`, `UNSUBSCRIBE`, `CANCEL MESSAGES`, `OPTOUT`) immediately set `contact.opted_out_all = True`.
  - An immutable audit record is logged in `conversation_handoffs` (`action="opt_out_triggered"`).
  - All future automated messages to the contact are strictly suppressed at the pre-dispatch gate.
- **Emergency Keyword Detection & Safety Handover**:
  - Inbound messages matching emergency keywords (`emergency`, `ambulance`, `severe pain`, `bleeding`, `chest pain`, `unconscious`) immediately trigger human takeover (`conversation.is_human_takeover = True`).
  - An audit record is logged in `conversation_handoffs` (`action="emergency_detected"`).
  - An emergency response is generated directing the patient to emergency hospital care (112), and clinic staff are alerted in the Live Inbox.
- **Human Takeover & AI Pause Enforcement**:
  - Conversations with `is_human_takeover=True` or `ai_paused=True` completely suppress automated AI processing.
  - Sending a manual staff reply or clicking "Take Over" cancels pending debounce jobs to prevent race conditions between AI and human operators.
- **Persistent Outbound Idempotency & Delivery Guarantees**:
  - Every outbound reply requires an atomic `OutboundIdempotencyKey` record. Duplicate messages with the same idempotency key are rejected.
  - Pre-flight gates re-verify `ai_mode == 'live'`, `is_human_takeover == False`, `ai_paused == False`, and `opted_out_all == False` immediately before network transmission.
  - Uncertain provider delivery outcomes are recorded with error details rather than retried blindly, preventing duplicate patient messaging.
- **Clinical Appointment Safety Boundaries**:
  - Autonomous appointment creation, rescheduling, and cancellation remain completely DISABLED in Task 9.
  - The read-only `check_availability` tool strictly enforces clinic operating hours (Monday to Saturday 09:00 - 20:00 IST) and Sunday closure via the authoritative `AppointmentService`.

### I. Controlled AI Appointment Workflows & Safety State Machine (Task 10)
- **Mandatory Default Policy Mode**:
  - `policy_mode` in `AppointmentWorkflowSettings` defaults strictly to `mode_a_read_only`.
  - In Mode A, Deepti is strictly read-only: she can answer questions and check availability, but ALL mutating tool operations (`create_appointment`, `reschedule_appointment`, `cancel_appointment`) are unconditionally blocked by the backend.
  - Mode B (`mode_b_staff_approval`) and Mode C (`mode_c_auto_commit`) require explicit, authenticated Owner/Admin configuration. Mode C remains disabled.
- **Backend Workflow State Machine Authority**:
  - The LLM can never directly book, reschedule, or cancel appointments.
  - All operations must transition through persistent state machine steps (`collecting_information` -> `checking_availability` -> `awaiting_slot_selection` -> `awaiting_patient_confirmation` -> `awaiting_staff_approval` -> `ready_to_commit` -> `committing` -> `confirmed`).
  - Mutations are committed exclusively by `AppointmentWorkflowService` invoking the authoritative `AppointmentService`.
- **Explicit Patient Confirmation & Anti-Hallucination Tokens**:
  - The system never treats an AI statement or unverified intent extraction as patient confirmation.
  - Slot selection generates a cryptographically random confirmation token (`conf_token`) and summary with an explicit expiration window (default 15 minutes).
  - Explicit affirmative confirmation (`YES`, `CONFIRM`) from the patient is mandatory before proceeding to staff approval or commit.
- **Staff Approval Queue Integrity**:
  - Mode B requires an authorized staff member (`Operator`, `Admin`, or `Owner`) to review and explicitly approve or reject the proposal.
  - Approval requests are tied to an immutable workflow version snapshot (`workflow_version`). If the patient requests changes, previous approvals become invalid.
- **Cross-Patient Isolation & Privacy**:
  - Read and mutate tools resolve patient context exclusively from the authorized WhatsApp conversation contact.
  - Cross-patient lookups are strictly blocked with `ACCESS_DENIED`. Patients cannot view, modify, or cancel appointments belonging to other individuals.
- **Transactional Idempotency & Conflict Protection**:
  - Commits require a unique idempotency key (`AppointmentOperationIdempotency`), preventing duplicate bookings caused by webhook retries or concurrent requests.
  - Availability is re-validated immediately before committing mutations.
  - Inbound WhatsApp replies and autonomous mutations remain disabled at the conclusion of Task 10.

### J. Durable Scheduled Automation & Outbound Kill Switch (Task 11)
- **Mandatory Default Global Kill Switch**:
  - `AUTOMATION_OUTBOUND_ENABLED` defaults strictly to `false` in configuration and database settings (`AutomationSettings.outbound_enabled = False`).
  - All new automation rules default to `is_enabled = False`.
  - An automation job never executes simply because its database record exists. Outbound transmission requires both rule-level enablement and global kill-switch activation.
- **12-Layer Safety Pre-Flight Gate (`EligibilityService`)**:
  - Immediately before WhatsApp transmission, every scheduled job passes through 12 non-bypassable safety gates:
    1. Global kill-switch check (`outbound_enabled == True`).
    2. Rule active check (`is_enabled == True`).
    3. Emergency stop check (`emergency_stop == False`).
    4. Contact consent check (`opted_out_all == False`).
    5. Promotional consent check (for marketing category messages).
    6. Human takeover check (`is_human_takeover == False`).
    7. WhatsApp 24-hour customer service window check (requires verified approved template outside 24h).
    8. Authoritative appointment status revalidation (cancelled/rescheduled appointments suppress pending reminders).
    9. Inactivity revalidation (patient replies or booked appointments suppress inactive follow-up stages).
    10. Business hours check (strictly enforces `Asia/Kolkata` 09:00–20:00 IST).
    11. Quiet hours protection (strictly suppresses or defers messages between 21:00–09:00 IST).
    12. Per-contact cooldown and rate limits (24-hour cooldown prevents spamming).
- **Immutable Suppression Audit Logging**:
  - Any blocked message is permanently recorded in `automation_suppression_logs` with the exact machine-readable reason code and contextual payload.
- **Worker Authentication & Concurrency Leasing**:
  - Worker cycles (`/api/v1/automations/process-due`) require authenticated staff sessions (`Owner`, `Admin`, `Operator`) or a verified `X-Worker-Token` matching `AUTOMATION_WORKER_SECRET_TOKEN`.
  - Concurrency safety is guaranteed by row leases with `FOR UPDATE SKIP LOCKED` and automatic lease expiration recovery (default 300s timeout).
- **Template Approval Integrity & Injection Prevention**:
  - Outside the 24-hour service window, only templates in `APPROVED` status can be dispatched.
  - Strict variable extraction and interpolation ensures missing variables throw `MissingTemplateVariableError` rather than sending blank or placeholder strings to patients.
- **Zero Real WhatsApp Outbound During Testing**:
  - Synthetic test mode (`payload["test_mode"] = True`) simulates full safety verification and state transitions without live WhatsApp API dispatch or external network egress.

### K. Controlled Campaigns, Instagram Re-engagement & Migration Security (Task 12)
- **Mandatory Default Draft Status & Double Approval**:
  - All campaigns default strictly to `draft` or `audience_prepared` status upon creation.
  - Outbound scheduling is strictly prevented until explicit authorization is granted by an authorized `Owner` or `Admin` role.
- **Approval Invalidation Invariant**:
  - Any mutation to campaign rules, copy, media attachments, or rate limits automatically invalidates prior approvals, increments the snapshot version counter (`current_version`), and reverts campaign status to `draft`.
  - Immutable audit logs in `campaign_approvals` track decision (`approved`, `rejected`, `invalidated`), reviewer ID, timestamp, and review notes.
- **Spreadsheet Formula Injection Sanitization (CSV)**:
  - During contact CSV ingestion, all cell values starting with formula execution prefixes (`=`, `+`, `-`, `@`) are automatically escaped with a leading single quote (`'`).
  - Phone numbers are validated against E.164 requirements and sanitized, strictly isolating raw spreadsheet strings from export views.
- **Deterministic Opt-Out & Consent Suppression**:
  - Contacts with `opted_out_all = True` or `opted_out_marketing = True` are strictly suppressed at the audience evaluation gate and re-checked immediately prior to dispatch.
  - Patients without explicit `marketing_promotions` consent are excluded by default for all promotional and re-engagement campaigns.
  - Patients with active confirmed upcoming appointments are excluded to prevent redundant re-engagement spam.
- **Legacy Migration Mutual Exclusion**:
  - To prevent dual-sending between legacy n8n/YCloud workflows and the new engine, the system enforces mutual exclusion: while in `legacy_active` or `shadow_comparison` cutover states, outbound campaign dispatches in the new engine are completely blocked.
- **Business Hours Window (09:00–21:00 IST)**:
  - Instagram re-engagement campaigns are strictly constrained to 09:00–21:00 Asia/Kolkata daily, deferring all out-of-window contacts to 09:00 IST the following morning.
- **Cross-Patient Data Isolation**:
  - Campaign recipient lists and analytics are scoped strictly to the Physio One organization, preventing cross-tenant or cross-contact data leakage.


### L. Production Security Hardening & Multi-Tier Worker Authentication (Task 13)
- **Multi-Tier Privilege Boundary for Internal Worker Routes**:
  - The privileged endpoints `/api/v1/automations/process-due`, `/api/v1/automations/scan-inactivity`, `/api/v1/campaigns/worker/run`, and `/api/v1/ai-inbound/process-due` are protected by `require_worker_auth` (`backend/app/core/worker_auth.py`).
  - **Google OIDC Token Validation**: Validates Google Cloud Tasks / Cloud Scheduler identity tokens (`accounts.google.com`), checking audience, expiration (with 30s clock skew window), and service account email (`WORKER_SERVICE_ACCOUNT_EMAIL`).
  - **Timing Attack Mitigation (HMAC)**: Validates `X-Worker-Token` against `AUTOMATION_WORKER_SECRET_TOKEN` using `hmac.compare_digest` in constant time, eliminating timing-based secret discovery.
  - **Strict Privilege Demarcation**: Ordinary dashboard users (`Operator`, `Viewer`) are strictly forbidden (`403 Forbidden`) from triggering background worker routines or modifying global automation settings. Only `Owner` and `Admin` sessions are permitted manual override execution.
- **Production Activation Safeguards**:
  - All automated capabilities are deployed in inert default states:
    - AI Receptionist Mode: `disabled`
    - Appointment Policy Mode: `mode_a_read_only`
    - Global Outbound Automations: `false`
    - Campaigns: `draft` / `paused`
    - Legacy Cutover: `legacy_active` (new engine blocked)
  - Zero autonomous dispatches can occur until intentional, audited administrative activation.

## Task 15 Security Hardening & Preflight Verification (2026-11-17)

- **Webhook Cryptographic Timing-Attack Resistance**:
  - Subscription challenge verification in `MetaCloudProvider.verify_subscription_challenge` updated to use `hmac.compare_digest` for constant-time token comparison.

- **Login Rate-Limiting & Brute-Force Lockout Defense**:
  - `LoginRateLimiter` enforces a 5-attempt sliding window (300s window) with a mandatory 10-minute (600s) lockout upon threshold exhaustion.
  - Tracking keys isolate attempts per IP and per normalized email address (`{ip}:{email}`).
  - Successful authentication resets attempt counters.
- **Strict Cookie Security Flag in Staging & Production**:
  - `set_auth_cookies` in `backend/app/api/v1/auth.py` updated to enforce `Secure=True` and `SameSite=lax` whenever `ENVIRONMENT in ("production", "staging")` or `COOKIE_SECURE=True`.
  - Ensures session and CSRF cookies are never transmitted over unencrypted HTTP in Cloud Run environments.
- **CORS Wildcard Rejection**:
  - `Settings` in `backend/app/core/config.py` enforces a Pydantic field validator that strictly rejects wildcard `*` origins in staging and production environments.
- **Controlled Tool Execution Sandbox**:
  - `ToolDispatcher` strictly enforces agent tool whitelists, RBAC caller permissions, and execution timeouts (15s).
  - Unauthorized or unregistered tool invocations are rejected and recorded in `AIToolExecution` audit logs.
- **Local Host Docker Binding**:
  - `docker-compose.yml` updated to bind PostgreSQL strictly to `127.0.0.1:${POSTGRES_PORT:-5432}:5432`, preventing exposure on external network interfaces.
- **Cloud Run & Cloud SQL Staging Network Hardening**:
  - Cloud SQL configured with `ipv4_enabled = true` and zero authorized networks (all direct internet TCP connections blocked).
  - Cloud Run connects via managed Cloud SQL socket volume (`/cloudsql/<instance_connection_name>`) and Google IAM credentials (`roles/cloudsql.client`), eliminating the expensive Serverless VPC Access connector while preserving zero-trust access.
  - Cloud Run environment variables for sensitive settings (`POSTGRES_PASSWORD`, `APP_SECRET`, `JWT_SECRET_KEY`, `AUTOMATION_WORKER_SECRET_TOKEN`) wired to Secret Manager secret versions.
